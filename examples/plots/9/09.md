# Example 09 — ALAFA-style leakage sweep

This note explains the plots in `examples/plots/9/` and the logic behind them.
The example itself is `examples/09_alafa_sweep.py`; the plots are produced by
`examples/plots/plot_09.py`.

## What the example does

ALAFA (Automatic Leakage Assessment for Fault Attack countermeasures) asks a
mechanical question, one fault site at a time:

> If I fault *this* instruction, does the signing code start leaking the secret
> key into its output?

Example 07 answered that for one hand-picked fault. Example 09 does it
**automatically** across 20 candidate sites — every operation call (`bl`) in the
Dilithium signing loop. For each site it installs an **instruction-skip fault**
(step the PC past the call, so the operation never runs), then runs a leakage
test and records the verdict.

We are **not** recovering a key. The whole framework only decides *leak / no
leak*. The detector uses just the emitted signatures and the challenge `c`
(re-expanded with the firmware's own `poly_challenge`) — no public key, no
secret.

## How "leak" is quantified

The test is the standard leakage-assessment one: **can two different secret keys
be told apart from their output?**

1. Sign the same messages under key A and key B.
2. Turn each signature into a feature vector: the **matched filter** of the
   sparse challenge `c` against each `z` polynomial (a negacyclic correlation).
   The *marginal* of `z` is secret-independent by design — a plain histogram sees
   nothing — so the signal only lives in the joint `(c, z)` relationship, which
   this projection extracts.
3. Score each signature by which key it looks more like:

   ```
   score(x) = <x, g_own_LOO> − <x, g_other>
   ```

   where `g_own`/`g_other` are the per-key mean feature vectors (templates) and
   `g_own_LOO` leaves the signature being scored out of its own template
   (leave-one-out, so a signature never helps classify itself). A key-A
   signature should score `> 0`; a key-B signature `< 0`.
4. **Accuracy** = fraction classified to the right key.
   `50%` = indistinguishable (no leak). `100%` = fully separable (leak).
   The example flags a site as **LEAK** at `accuracy ≥ 80%`.

> Why leave-one-out matters: the feature space is 1024-dimensional with only ~56
> samples. If we projected onto the in-sample mean-difference axis, even random
> noise would look separated. Leave-one-out removes that self-fulfilling bias, so
> the control (no-fault) case correctly reads as overlapping.

## The plots

### `alafa_accuracy.png` — the sweep verdict

One horizontal bar per fault site, its two-key classifier accuracy.

- **blue** = control (no fault)
- **red** = LEAK (accuracy ≥ 80%)
- **green** = ok (ran, but near chance — no leak)
- **grey** = crash/hang (the skip broke signing; the fault destabilises the code
  rather than leaking, so the per-signature test can't assess it)

Dashed line = the 80% leak threshold; dotted line = 50% chance.

**Result:** exactly one site crosses the threshold — `z = z + y (polyvecl_add)`
at `0x4d5e`, at 100%. Everything else either crashes or sits at chance.

### `distributions.png` — the distributions being compared

A grid of six representative sites. Each panel overlays the **two keys' score
distributions** (key A blue, key B orange) with the classifier's decision
boundary dashed at 0.

- **control (no fault):** the two histograms sit on top of each other, straddling
  the boundary — the output hides which key produced it.
- **`z = z + y` (LEAK):** key A piles up entirely on one side of 0, key B
  entirely on the other — cleanly separated. The output now reveals the key.
- **`w → invNTT`, `pack w1`, `reduce z`, `w0 − c*s2`:** all overlapping like the
  control — these skips don't leak (they either don't touch the mask or the mask
  survives).

Overlap = hidden. Separated = leak. That visual contrast *is* the assessment.

`score_<site>.png` are the same six panels saved individually.

## Why `z = z + y` is the one that leaks

Dilithium's response is `z = y + c·s1`, where `y` is a fresh secret nonce that
**masks** the secret term `c·s1`. In this firmware the masking add is:

```
0x4d5e   bl  polyvecl_add        ; z = z + y   (z already holds c*s1)
```

Skip that call and `z = c·s1` — the mask is never applied, so the response
carries the secret directly. The matched filter then aligns `z` with `c` and the
two keys separate immediately. This is a documented fault: **category 4.2** of
the fault-attack catalog (Ravi/Jhanwar et al. 2019, *Exploiting Determinism*;
ElGhamrawy 2023; Du 2025).

Two honest caveats the plots make visible:

- **The rejection-check faults don't show up here.** The checks (`z-norm`, `r0`,
  `ct0`) *are* the zero-knowledge mask, and faulting them does leak — but into a
  lattice/polytope problem over *many* signatures (that's example 08), not a
  per-signature two-key distinguisher. Here their whole-call skips just
  crash/hang, so this detector can't see them. Different fault class, heavier
  analysis.
- **The sweep does not rediscover category 4.1** (loop-abort on `y`). That attack
  zeroes *part* of the nonce, which a whole-call skip can't express — skipping
  the entire `y` sampler crashes signing instead. Representing 4.1 would need a
  finer fault (abort part-way through `poly_uniform_gamma1`).

So example 09 is honestly scoped: it is a detector for **high-SNR mask-removal
faults**, and it cleanly separates them from the check-bypass class that needs
the heavier statistical machinery of example 08.

## Why most sites "crash/hang"

Instrumenting every grey site (`examples/plots/diag_crash.py`) shows they are
**not crashes — they are hangs**: every one runs to the 20M-instruction cap
(a real memory fault would die in a few thousand instructions). None segfault.

The cause is the reject-and-retry structure of signing:

```
loop:
    sample y;  w = A·y;  decompose w;  c = challenge(w1)
    z = c·s1;  z += y;   reduce
    if ‖z‖  ≥ bound: goto loop          # reject
    r0 = w0 − c·s2;  if ‖r0‖ ≥ bound: goto loop
    ct0 = c·t0;      if ‖ct0‖ ≥ bound: goto loop
    make_hint;       if weight too big: goto loop
    return sig
```

A whole-call skip drops a value some rejection check depends on, so the check
sees garbage, **fails every iteration, and the loop never accepts** — it spins
until the cap. Two sub-cases:

- **Skip a compute step** (`sample y`, `decompose w`, `c*s1`, `c*s2`,
  `poly_challenge`, `c*t0`, `make_hint`): the norm being checked is now computed
  from stale/uninitialised data, which almost always exceeds its bound → perpetual
  reject.
- **Skip a `chknorm` call itself** (`z-norm`, `r0`, `ct0`): `poly_chknorm` returns
  its verdict in `r0`; skip the `bl` and `r0` holds a leftover **nonzero** value
  from the previous op, so `cmp r0,#0; bne reject` rejects every time.

That last case is the important one, and it is why the rejection-check faults are
absent from the ALAFA results even though they *do* leak (example 08).
**Skipping a check and forcing its verdict are opposite faults:**

| | fault model | effect | outcome |
|---|---|---|---|
| sweep (09) | skip the whole `bl poly_chknorm` | `r0` = stale ≠ 0 → always **reject** | hang |
| example 08 | force the `cmp` result to 0 | `r0` = 0 → always **accept** | leak |

So a whole-call skip breaks the loop in the *wrong* direction to expose the
check-bypass leak; that leak needs the targeted stuck-at-accept fault of example
08. (One borderline site, `shake squeeze` @ 0x4d18, completes on a single sign but
fails on some messages, so the sweep — which bails on the first failure across all
signatures — still marks it crash/hang.)

## Auto-discovered fault sites (no hard-coded address table)

The sweep sites used to come from a hand-authored 20-entry address table
(`SIGNING_SITES`, `0x4c7c … 0x4e32`) baked into the Dilithium profile — a
firmware-build-specific config that had to be re-derived by hand for every new
ELF. That table is gone. The framework now **discovers the sites automatically**:
`profile.fault_sites` disassembles the resolved signing function
(`crypto_sign_signature_ctx`, descending through any thin wrapper) and takes
every `bl`/`blx` in its body as a whole-call skip site. Any new scheme's sweep
sites are found the same way, zero-config (MAYO descends the 1-call
`crypto_sign_signature` wrapper into `mayo_sign_signature`).

**Fault-coverage diff — does any fault stop existing?** No. Discovery is a strict
**superset**: all 20 curated sites appear among the 48 auto-discovered ones, and
the `z = z + y` mask add at `0x4d5e` — the only site that leaks — is still
flagged LEAK. Verified directly: *curated sites NOT discovered = NONE*. The 28
extra sites are the setup/bookkeeping calls the curated table had skipped by hand
(`unpack_sk`, `shake256_inc_*`, `randombytes`, `matrix_expand`, `poly_ntt`,
`poly_invntt`, `polyveck_reduce`/`caddq`, `poly_add`, `pack_sig`, …). Every one
reads **crash/hang or no-leak** — none is a new leak — so the verdict is
unchanged, only the grey rows multiply.

**Running time.** The extra sites are not free, and the cost is worse than the
site count suggests:

| sweep | sites | N/key | wall-time |
|---|---|---|---|
| curated (hand table) | 20 | 12 | **52.3 s** |
| auto-discovered | 48 | 12 | **299.6 s** (~5.7×) |

The slowdown is **~5.7×, not the ~2.4× the 48/20 site ratio predicts**. The
reason is exactly the hang mechanism above: most of the 28 extra sites are
load-bearing setup calls whose whole-call skip makes signing **fail every
rejection iteration and spin to the 20M-instruction cap** (§"Why most sites
crash/hang"), rather than dying fast. A hang site costs ~20M instructions ×
N × 2 keys; a curated leak/no-leak site costs a normal signing. So runtime is
dominated by how many sites *hang*, not by the raw site count — and auto-discovery
adds mostly hang sites. The trade accepted: fully automatic, firmware-agnostic
site generation in exchange for a slower sweep dominated by grey rows that the
curated table had pruned by hand. (Labels also become `bl <symbol>` instead of
hand-authored strings.)

## Parallel sweep (`-j`)

Every fault site is independent — each is isolated on a clean machine snapshot
(`_run_site` snapshots on entry and restores on exit), its inputs (the two keys,
the messages, the per-key nonces) are deterministic from `(elf, keys, N)`, and
its skip `Injector` is detached afterwards. So the sweep parallelises cleanly:
give each worker the ELF path and a site, let it rebuild its own emulator and run
that site. The `-j` flag does this over a process pool (spawn), and the result is
**bit-identical** to the serial run (re-ordered only) — the parity is asserted,
not approximate, in `tests/run_tests.py::test_parallel_sweep_matches_serial`.

> Per-site isolation is load-bearing, not decorative. Without it, a faulted or
> hung signing leaves the guest machine dirty and the *next* site on the same
> worker inherits that state — so a site's verdict depends on which site ran
> before it. Serial hid this (fixed order → reproducible, though small-N sweeps
> showed spurious near-threshold leaks); a pool schedules sites in a varying
> order, which turned the contamination into run-to-run **non-determinism** until
> the snapshot/restore fix landed on `master`.

| sweep | sites | N/key | wall-time |
|---|---|---|---|
| serial (`-j1`) | 48 | 12 | **~300 s** |
| parallel (`-j20`) | 48 | 12 | **~18 s** (~16×) |

```
python -m ucpqc sweep firmware/ml-dsa-44_m4f_test.elf --n 12 -j20
  -> 1 leaking site(s): 0x4d5e bl pqcrystals_dilithium_polyvecl_add   (same verdict)
```

The speedup (~17× on 20 CPUs, ~16 cores busy) is close to the CPU count but
**floored by the slowest single site, not the total**: the ~28 hang-to-cap sites
cost ~20M instructions each and, with more workers than hang sites, the pool
clears them in roughly `ceil(n_hang / workers)` waves — so wall-time approaches
one hang-site's ~cap time plus scheduling, and adding CPUs past that point buys
little. One task per site (not chunked) + `as_completed` is what keeps the pool
busy despite that extreme skew; a static split would strand several hang sites in
one worker.

**Memory.** The cost of processes is RAM: each worker is a full interpreter with
its own emulator, so `-j20` peaks at **~1.7 GB** resident (≈ 20 × ~85 MB). The
sibling `parallel-freethreading` branch runs the identical sweep as threads in
one address space and peaks at **~156 MB** at `-j20` (~72 MB base + only the
per-thread guest state of each extra machine) — **~11× less memory** — at a small
wall-time cost (~22 s vs ~18 s here). That is the backend trade-off: processes are
slightly faster and need no special interpreter; threads are far more memory-frugal
but need a free-threaded 3.14t build. Both hook the same per-site seam, so
`master`'s serial code stays the reference.

## A t-test version of the verdict

Accuracy is intuitive but it is not a calibrated statistic. `ttest_09.py`
re-expresses the same "are the two keys distinguishable?" question as proper
significance tests, and produces two more plots.

### The classic leakage t-test: TVLA per coordinate

TVLA (Test Vector Leakage Assessment) runs a **two-sample Welch t-test at every
measurement point** between two populations and flags any point with `|t| > 4.5`
(≈ two-sided `p < 1e-5`). Here the "measurement points" are the 1024
matched-filter coordinates, and the two populations are key A's vs key B's
signatures. There is **no data-derived direction** in this test, so its p-values
are honest.

This is the same test that was **blind on the raw `z` coefficients** (max
`|t| ≈ 3.4`, below threshold — `z`'s marginal is secret-independent by design).
The point is that the *identical* t-test, applied to the c-aware matched-filter
feature, is no longer blind at a leaky site.

Results (N=28/key):

| site | TVLA max\|t\| | # coords > 4.5 | verdict |
|---|---|---|---|
| control (no fault) | 3.6 | 0 | no leak |
| every non-crashing site | 3.3 – 3.9 | 0 | no leak |
| **z = z + y** (0x4d5e) | **15.4** | **444** | **LEAK** |

The non-leaky sites all sit at `max|t| ≈ 3.3–3.9` — that is just the noise
ceiling for the largest of 1024 near-null t-values (and it matches the raw-`z`
number). Only the mask-removal fault pushes hundreds of coordinates far past 4.5.

### Two supporting statistics

- **Welch t on the 1D discriminant score** (the leave-one-out score s0 vs s1):
  an *effect-size* readout of the whole detector. Control `t = −0.68` (`p = 0.5`);
  `z=z+y` `t = 129` (`p ≈ 8e-69`). Because the score uses data-derived templates,
  this parametric p is optimistic — so it is backed by:
- **Permutation p-value on the accuracy** (assumption-free): shuffle the key
  labels 2000×, recompute leave-one-out accuracy, and see how often chance reaches
  the real separability. Control `p = 0.46` (nothing there); `z=z+y` `p = 0.0005`
  (the floor, 1/2001 — never once matched by a shuffle). This is immune to the
  data-derived-direction concern, and it confirms the parametric verdict.

### `tvla_trace.png` — the t-test picture

Per-coordinate `|t|` across the 1024 features, one panel per representative site,
with the 4.5 threshold dashed. Control and the ok sites hug the bottom, entirely
under the line; `z=z+y` is lifted bodily above it. This is the canonical TVLA
leakage plot.

### `tvla_maxt.png` — the t-test verdict per site

Bar chart (log scale) of `max|t|` per fault site, with the 4.5 threshold. Every
non-leak site clusters at ~3.5; `z=z+y` alone stands at 15.4, past the line. It is
the t-test twin of `alafa_accuracy.png`.

## Reproducing

```bash
.venv/bin/python examples/09_alafa_sweep.py        # the ASCII sweep
.venv/bin/python examples/plots/plot_09.py         # distribution plots
.venv/bin/python examples/plots/ttest_09.py        # t-test plots + table
```

`plot_09.py` and `ttest_09.py` take optional `[firmware.elf] [n_per_key]`; both
default to 28 signatures per key (larger than the sweep's 16, so the histograms
are smooth, the t-tests have enough samples, and the near-chance sites settle
honestly).
