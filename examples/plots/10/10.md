# Example 10 — intra-function instruction-skip faults

This note explains the plots in `examples/plots/10/` and the capability behind
them. The tool is `examples/10_intra_function_skip.py`; the plots are produced
by `examples/plots/plot_10.py`. The reusable machinery lives in
`ucpqc/replay.py` and `ucpqc/detectors.py`.

## What it does

Example 09 faults **whole calls** (`bl` sites) in the signing loop. This tool
faults **individual instructions inside a chosen function**, and does it without
re-running the whole signature each time.

The trick is capture-and-replay:

1. **Capture once.** During N golden signings (per key), record the target
   function's inputs and outputs at one invocation — via `Recorder`, built on the
   entry/return boundaries of `tracing.Trigger`.
2. **Replay in isolation.** For each instruction-skip site, restore/rebuild just
   that function's entry state and run *only that function* (a few thousand
   instructions) under the fault — never the whole signing again.
3. **Detect.** Feed the faulted outputs to a detector whose kind matches the
   target's role (two-key for secret-dependent outputs; spec-aware for the
   rejection decision).

A full ML-DSA signing is ~1.5M instructions; one `polyvecl_add` replay is ~6.2k
— so a fault trial is **~240× cheaper** than re-signing.

## Two replay backends (and the benchmark)

`backend_cost.png` compares them on one `polyvecl_add` capture:

- **snapshot resume** — restore full machine state (registers + memory), then run
  from the entry PC to the captured return PC. Works for **any code region** and
  any function; **1.03 ms/trial**, **9.4 MB stored per capture**.
- **`m.call`** — rebuild the call from captured args on a fresh stack. Needs the
  argument signature and a real function target (not an inline region), and
  relocates input buffers (preserving pointer aliasing for in-place ops like
  `z = z + y`). **0.62 ms/trial**, **8 KB stored per capture** (~1150× smaller).

Both execute the same 6.2k instructions and produce **identical** outputs
(`equivalent: True`). `m.call` is the default for function targets; the snapshot
backend is required for the 4.3 region below.

## The plots

### `intra_skip_accuracy.png` — catalog §4.2 (response computation)

An instruction-grained ALAFA sweep: one bar per instruction *inside*
`polyvecl_add` (the `z = z + y` step), coloured by the two-key matched-filter
accuracy of the faulted output. Two sites hit **100% (LEAK)**:

- `0x4d5e … bl poly_add` — persistently skipping the call means the add never
  happens, so `z` stays `c·s1` (the mask is never mixed in). This is the
  instruction-level rediscovery of example 09's whole-call `z=z+y` leak, i.e.
  **Ravi 2019 (skip-addition) / ElGhamrawy 2023 / Du 2025**.
- `mov r7, r0` — corrupts the output pointer so the add writes elsewhere, leaving
  the `c·s1` buffer intact: same effect.

Every other instruction sits at chance (no leak) or crashes the function. The
matched-filter two-key detector is the right one here because the response is
**secret-dependent** — the same detector, and the same ~100%, as example 09.

### `rejection_flip.png` — catalog §4.3 (rejection bypass / "Finding a Polytope")

Region replay over the r0 rejection decision
(`bl chknorm ; cmp ; bne reject ; …accept`). We capture a mix of in-spec and
out-of-spec `r0` states, then skip each instruction of the decision and see how
many out-of-spec `r0` (which *should* reject) get wrongly accepted.

**Only skipping the reject branch (`bne @ 0x4dde`) bypasses the check** — 100% of
out-of-spec `r0` are then released; skipping the `bl chknorm` or the `cmp` does
nothing (0%). This confirms the point established analytically: the load-bearing
instruction is the **caller's branch**, not anything inside `chknorm` (whose
verdict is a 256-coefficient reduction no single interior skip can flip). The
wrongly-released out-of-spec `r0` are exactly the input to the polytope attack
(**Azevedo-Oliveira et al. 2025**); the leak itself is quantified in example 08.

Because the decision is inline code (not a function), this demo is **snapshot
backend only** — the reason both backends exist.

## Why the detector must match the target's role

Not every faulted output is secret-dependent. For `z = c·s1` the two-key test
fires (the response carries the key). For the rejection decision the signal is a
support violation, caught by the spec-aware band-`‖r0‖∞` test (example 08). And
for the nonce sampler `y` (catalog §4.1, not plotted here) a two-key test would
be *blind* — `y` is key-independent — so the correct detector is a
uniformity/bias test on `y`, with the two-key test applied only after propagating
to `z`. `ucpqc/detectors.py` carries all three.

## Reproducing

```bash
.venv/bin/python examples/10_intra_function_skip.py     # the ASCII tool + benchmark
.venv/bin/python examples/plots/plot_10.py              # these three plots
```

Both take optional `[firmware.elf] [n_per_key]`. The tool first prints the call
graph of one signing (the target-selection front end), then runs the 4.2 sweep,
the backend benchmark, and the 4.3 region demo.
